## 0. 어떻게 검증했는가 (신뢰도 읽는 법)

## 2. 발행기·워커·DB (P)
**P1 | Critical | `app/publishing/tistory.py:426-454` (재현)**
- 비공개 라디오를 클릭하는 블록이 `try/except Exception: pass`로 감싸져 있고, 선택 상태를 되읽는 코드가 어디에도 없다(`is_checked`/`input_value`/`aria-checked` 검색 결과 없음).
- 최종 버튼 후보의 첫 항목이 `button:has-text('공개 발행')`이다. 비공개 옵션이 없거나(라벨 변경), 숨겨진 input이 DOM에서 먼저 잡히거나, 클릭이 먹지 않으면 기본 상태에서 공개 발행이 눌린다.
- 로컬 대역으로 3가지 시나리오 모두 `visibility=PUBLIC`, `publish()`는 정상 반환. YAML 선택자를 새 라벨로 고쳐도(README가 안내하는 방식) 결과는 같았다.
- 클래스 docstring은 "fails closed"라고 하고, 설계 문서(`docs/아키텍처_설계안.md:943`)는 "선택자를 못 찾으면 발행하지 않는 것이 정답"이라고 쓰는데 구현과 반대다.
- 수정: `check()` 후 `is_checked()` 단언, 실패 시 최종 클릭 전에 `UI_BROKEN`. 최종 버튼은 비공개 동작 버튼만 후보로 두고 "공개 발행"·`.btn-primary`·"저장"은 제거. 가시성·최종 클릭에서 `force=True`와 `except: pass` 제거. 어댑터가 `draft.visibility == "PRIVATE"`를 단언. 비공개 옵션이 없으면 클릭이 0회임을 검증하는 가짜 Page 테스트 추가.
- **→ 수정함.** `_publish_as_private`: 비공개 옵션 후보(보이는 요소부터)를 눌러 `is_checked()`로 선택을 증명한다(라디오가 아닌 컨트롤만 `aria-checked`·클래스 토큰으로 판정). 비공개를 골랐는데 보호·공개 라디오가 선택돼 있으면 중단한다. 증명하지 못하면 최종 버튼을 **한 번도 누르지 않고** `UI_BROKEN`. `button:has-text('공개 발행')` 후보를 없애고, 어떤 버튼이든 누르기 전에 문구를 읽어 '공개'(비공개 제외)가 남은 버튼과 `임시저장`은 건너뛴다. `force=True`와 `except: pass`를 이 경로에서 없앴고 `publish()`가 `visibility == "PRIVATE"`를 단언한다.
- **재확인(제가 직접 실행):** 리뷰어의 가짜 Tistory + 실제 Chromium 시나리오 7개를 수정 후 코드로 다시 돌렸다. 비공개 옵션 이름이 바뀐 경우(S1·S3·S4)와 클릭이 먹지 않는 경우(S2), 최종 버튼이 없는 경우(S5), 본문이 주입되지 않은 경우(S6)는 모두 `UI_BROKEN`으로 멈추고 글이 만들어지지 않았다(리뷰 당시에는 모두 **공개 발행**). 정상(S0)과 숨은 input이 앞에 있는 경우(S1b)는 서버에 비공개 글로 기록됐다. **실제 Tistory UI는 여전히 검증하지 못했다.** 가정 A1–A12(A9–A12는 2차 리뷰 반영분)은 `tistory.py` 머리말에 적혀 있고, 처음 쓰기 전에 비공개 글 1건으로 수동 드라이런이 필요하다. **2차 리뷰에서 이 수정의 구멍(레이어 열기 클릭, 중립 문구, 경쟁)이 더 나와 §2.1에서 막았다.**

**P2 | High | `tistory.py:64-71, 79-94, 463-483` (재현)**
- `verify_private`는 "제목이 있으면서 URL에 `manage`가 없으면 실패"만 본다. HTTP 상태나 `private_marker`를 쓰지 않는다. `&`·`<`·`>`가 든 제목은 DOM에서 이스케이프되어 일치하지 않고, 공개 슬러그에 `manage`가 들어가면(`/entry/how-to-manage-money`) 검사를 건너뛴다.
- `publish()`는 `page.url`을 글 URL로 받아들인다. `/manage/posts/`로 리다이렉트돼도 통과하고, 익명 검사는 로그인 화면만 본다.
- `_verify_owner_content`는 `not (has_title or is_valid_url) and not has_body`일 때만 실패한다. 제목 첫 단어, URL에 `entry` 또는 숫자, 본문 첫 5단어 중 하나만 맞아도 통과한다.
- 재현: 공개 글 + `/manage/posts/` 리다이렉트 → `Job SUCCEEDED, PublishJob VERIFIED, Article VERIFIED`, 서버 실제 값은 PUBLIC.
- 수정: 엄격한 퍼머링크 형식만 허용(`/manage/` 거부), unescape한 내용 비교, 익명에서 "접근 불가"의 양의 증거(403/404/로그인 리다이렉트/마커) 요구, 소유자 검사는 AND 조건, 증명하지 못하면 실패.
- **→ 수정함.** 글 주소는 `/숫자`·`/entry/슬러그` 형식만 인정하고(`/manage…`·티스토리 메인 거부) 아니면 최근 글 목록에서 제목으로 찾으며, 그래도 없으면 `PUBLISH_UNVERIFIED`. 소유자 검사는 제목과 본문 앞 5단어를 **모두** 요구한다(엔티티·공백 정규화). 익명 검사는 `/manage`가 아닌 곳에서 제목·본문이 보이면 실패시키고, HTTP 401/403/404, 글 페이지 밖으로의 이동, 비공개 문구 중 하나를 '양의 증거'로 요구하며 근거를 `verification_details.evidence`에 남긴다. 리뷰어의 `exp_verify_logic` 시나리오 10개(소유자 검사 5개, 익명 검사 5개)를 다시 돌리면 9개가 `PUBLISH_UNVERIFIED`로 실패한다(리뷰 당시에는 대부분 통과했다). 나머지 1개는 존재하지 않는 주소의 404를 비공개 증거로 받는 설계이며, 틀린 주소는 먼저 도는 소유자 검사가 거른다. **남은 위험(2차 리뷰 뒤 갱신):** 봇 차단 화면의 403·리다이렉트가 공개 글을 비공개로 오인시키는 문제는 §2.1 R3에서 대조군·일반 UA·2회 확인으로 줄였다. 글 주소만 막는 차단은 여전히 구분하지 못한다. 드라이런 때 이미 공개된 글을 익명으로 열어 200과 제목이 보이는지 확인할 것.

**P3 | High | `tistory.py:74-75, 456-461`, `worker.py:64-87`, `app/web/app.py` retry (재현)**
- 검증이 실패하면 워커가 `post.url`을 버린다(`result_url` 저장·로그 없음). 클릭 이후 예외도 `UI_BROKEN`으로 뭉개진다.
- retry 엔드포인트는 VERIFIED 글을 포함해 어느 상태에서든 PENDING으로 되돌리고 `result_url`을 지우지 않는다. 대시보드는 DRAFT가 아닌 모든 행에 "재등록"을 보여 준다. 재현에서 다음 워커 실행 후 Tistory에 글이 2개.
- 수정: 알게 된 즉시 `result_url` 저장, 최종 클릭 전 PUBLISHING을 커밋(write-ahead), VERIFIED·RUNNING·미확인 잡은 409, 재발행 전 `/manage/posts`에서 정확한 제목 검색.
- **→ 수정함(발행기·워커 부분).** 어댑터가 최종 클릭 직전에 플래그를 세워, 그 뒤의 모든 예외(`UI_BROKEN` 포함)를 글 주소를 실은 `PUBLISH_UNVERIFIED`로 바꾼다. 워커는 주소를 알게 된 즉시 커밋하고 실패 메시지에도 주소를 붙인다. `PUBLISH_UNVERIFIED`는 자동 재시도하지 않는다. 웹의 재등록 가드는 §3에서 다룬다. **하지 않은 것:** 재발행 전에 제목으로 기존 글을 찾는 단계.

**P4 | High | `jobs/queue.py:13-37`, `worker.py:20-70` (재현)**
- `locked_at`은 쓰기만 하고 읽지 않는다. PUBLISHING 상태와 JobRun이 flush만 되고 커밋되지 않은 채 몇 분짜리 브라우저 단계에 들어간다. 강제 종료한 워커 프로세스 1주일 뒤에도 `claim_next() → None`.
- 수정: 브라우저 실행 전 커밋, 임대(TTL) 후 수동 확인 상태로 전환(자동 PENDING 금지), `BaseException` 처리, 통계에 RUNNING 표시.
- **→ 수정함.** 클레임·`JobRun`·PUBLISHING을 브라우저 단계 전에 커밋한다(워커가 죽어도 흔적이 남고 DB 락을 쥔 채 브라우저를 돌리지 않는다). `publish_lock_ttl_seconds`(기본 1800초)를 넘겨 RUNNING인 잡은 FAILED/`STALE_RUNNING` + PublishJob `PUBLISH_UNVERIFIED` + Article·Version QUARANTINED로 멈추고 **절대 PENDING으로 되돌리지 않는다**. `KeyboardInterrupt`·`SystemExit`는 FAILED/`INTERRUPTED`로 기록한 뒤 다시 던진다. **재확인(제가 직접 실행):** 워커 프로세스를 `publish()` 도중 강제 종료하고 잠금 시각을 2시간 전으로 돌린 뒤 다른 워커로 `run_once`를 실행하면 잡이 `STALE_RUNNING`·`QUARANTINED`로 정리되고 발행기는 다시 불리지 않는다. **남은 한계:** 아주 느리지만 살아 있는 발행(30분 초과)은 만료로 오인될 수 있고, 만료 시각은 `PUBLISH_LOCK_TTL_SECONDS`로 조절한다(2차 리뷰 뒤 하한을 600초로 올렸고 락 하트비트는 없다). PUBLISHING 커밋 전에 죽은 잡은 글이 없으므로 격리하지 않는다(§2.1 R9). 대시보드가 `QUARANTINED`·`STALE_RUNNING`·`INTERRUPTED`·`last_outcome`을 보여 주도록 하는 작업은 하지 않았다.

**P5 | Medium** 실패 시 Article/ArticleVersion이 PUBLISHING에 남는다. `QUARANTINED`는 정의만 있고 어디서도 할당하지 않는다(검색 확인). `run_once`가 성공·실패 모두 True를 반환해 대시보드가 "성공"이라고 말한다(재현).
- **→ 수정함.** `PUBLISH_UNVERIFIED`·`UI_BROKEN`·`AUTH_REQUIRED`·예상 밖 오류는 Article·Version을 QUARANTINED로 두고, 발행이 막혔을 뿐인 `PREFLIGHT_FAILED`는 `READY_TO_PUBLISH`로 돌린다. `run_once`의 bool 반환은 그대로 두고 `last_outcome`(`SUCCEEDED`·`FAILED`·`DISABLED`·`NONE`)을 새로 노출한다. 대시보드가 이 값을 쓰도록 바꾸는 일은 하지 않았다.
**P6 | Medium** 킬 스위치를 클레임 이후에 검사해 실행할 때마다 잡 1개가 영구 FAILED/BLOCKED가 된다. 썸네일 경로가 CWD 기준 상대 경로로 저장되어 다른 디렉터리에서 시작한 워커가 잡을 소진한다(재현).
- **→ 수정함.** 킬 스위치를 클레임·만료 복구보다 먼저 검사한다(꺼져 있으면 잡을 건드리지 않고 `DISABLED`). 썸네일은 절대 경로로 저장하고, 상대 경로로 저장된 기존 값은 작업 디렉터리 → 저장소 루트 순으로 찾는다.
**P7 | Medium** README의 "소스코드 수정 없이 YAML 수정만으로 대응"은 사실이 아니다. 필수로 로드하는 선택자 12개 중 3개만 쓰이고 나머지는 하드코딩이다. 블로그 신원은 메인 페이지에서 한 번만 확인하고 에디터 페이지에서는 확인하지 않는다(재현).
**P8 | Medium** 카테고리·HTML 모드·썸네일·태그·본문 주입 실패를 모두 삼킨다. 본문 주입이 불가능해도 빈 글이 `Article VERIFIED`가 된다(재현). 주입 후 값을 되읽어 검증해야 한다.
- **→ 수정함(핵심 부분).** 본문 주입 뒤 제목과 본문을 에디터에서 되읽어(CodeMirror·textarea·TinyMCE) 제목이 다르거나 본문 앞 단어를 어디서도 찾지 못하면 발행 레이어를 열기 전에 `UI_BROKEN`. 주입·되읽기 스크립트 오류도 `UI_BROKEN`. 카테고리·태그·썸네일·HTML 모드 전환은 여전히 best-effort이지만 이제 실패를 로그로 남긴다(`_select_category`·`_switch_to_html_mode`는 `force=True` 클릭을 그대로 쓴다).
**P9 | Low** `retryable=True`를 만드는 곳이 없어(검색 확인) `RETRY_WAIT`·`max_attempts=2`가 사실상 죽은 코드다. 같은 프로필로 워커 2개가 뜨면 두 번째가 실패한다.

**P10 | Low** `20260730_02` downgrade가 MySQL에서 비원자적이다(안전 검사 전에 테이블을 지움).
- **→ 수정함.** DRAFT 행 검사를 테이블을 지우기 전에 하고 `articles`·`article_versions` 둘 다 본다. SQLite에서 upgrade → downgrade → upgrade를 돌려 확인했고, MySQL 전용 분기는 실행하지 못했다(읽어서만 확인).

## 3. 웹 대시보드·CLI·설정 (W)
**W1 | High | `app/web/app.py` 전반, `cli.py:40,62` (재현)**
- 인증·Origin·Host 검사·CORS 설정이 없다. 본문이 없는 POST는 단순 요청이라 Chromium에서 다른 사이트가 실행할 수 있었다: `run-worker`, `topic-candidates/discover`, `topic-candidates/{id}/generate-article`, `articles/{id}/retry`(서버 로그 200, 유료 호출 로그 확인). DELETE와 JSON POST는 preflight(405)로 막혀 도달하지 못한다.
- `retry` 후 `run-worker`면 `headless=False`인 브라우저가 운영자 데스크톱에 열려 로그인된 프로필로 재발행한다.
- Host 헤더 검증이 없어 DNS 리바인딩으로 글 본문 조회와 삭제가 가능했다. `--host 0.0.0.0`이면 LAN 전체에 열리는데 경고가 없다.
- `POST /api/articles/generate`가 막힌 것은 설치된 FastAPI의 `strict_content_type` 덕분이다. `pyproject.toml`은 `fastapi>=0.100.0`이라 구버전에서는 이것도 뚫린다.
- 한계: 실제 공개 사이트 → 루프백 요청이 최신 Chromium의 Local Network Access 프롬프트에 막히는지는 확인하지 못했다.
- 수정(검증됨): `TrustedHostMiddleware(["127.0.0.1","localhost"])` + 상태 변경 요청에서 `Sec-Fetch-Site`가 있고 `same-origin`/`none`이 아니면 403. 두 장치를 넣자 공격 4건이 모두 403이고 같은 출처 UI 흐름은 정상. 루프백이 아닌 `--host`는 토큰/기본 인증 없이는 거부.
- **→ 수정함.** `DashboardGuardMiddleware`(가장 바깥의 순수 ASGI 미들웨어)가 차례로 검사한다. ① Host가 `DASHBOARD_ALLOWED_HOSTS`(기본 `127.0.0.1,localhost,::1`)에 없으면 400(DNS 리바인딩 차단, IPv6 `[::1]:포트` 해석 포함). ② GET·HEAD·OPTIONS가 아닌 요청의 `Sec-Fetch-Site`가 `same-origin`·`none`이 아니거나(`same-site` 포함) `Origin`이 Host와 다르면(`Origin: null` 포함) 403. ③ `DASHBOARD_PASSWORD`가 있으면 모든 경로(정적 파일·`/docs` 포함)에 HTTP Basic 인증을 요구하고 아이디·비밀번호를 모두 상수 시간으로 비교한다. 모든 응답에 CSP·`nosniff`·`X-Frame-Options: DENY`·`Referrer-Policy`를 붙인다. CLI는 루프백이 아닌 `--host`에 비밀번호가 없으면 시작하지 않고 종료 코드 2로 끝난다. **재확인(제가 직접 실행):** 리뷰어의 실제 Chromium 공격(다른 출처 페이지에서 보낸 단순 POST 5건)이 서버 로그에 모두 403이고, 수정 전에 실행되던 워커·유료 생성 호출·후보 상태 변경이 일어나지 않았다. 리바인딩 호스트(`rebind.attacker.test`)로는 GET·DELETE·POST가 모두 400이고, 정상 호스트(`127.0.0.1`)는 200이다.
- **알아 둘 점:** ① Windows 레지스트리가 `.js`를 `text/plain`으로 연결한 PC에서는 `nosniff` 때문에 브라우저가 `main.js` 실행을 거부해 대시보드가 빈 화면이 된다(실제 브라우저 점검에서만 발견). `.js`·`.mjs`·`.css` MIME을 코드에서 고정했다. ② `0.0.0.0`·PC 이름·LAN IP로 접속하면 그 이름을 `DASHBOARD_ALLOWED_HOSTS`에 넣기 전까지 400이다. ③ 리버스 프록시는 원래 Host 헤더를 유지해야 한다(Origin과 비교한다). ④ CSP 때문에 `/docs`·`/redoc` 화면은 CDN 스크립트가 막혀 빈 화면이다(`/openapi.json`은 동작하고 인증 대상이다). ⑤ 처리되지 않은 예외로 나가는 500 응답에는 보안 헤더가 붙지 않는다.

**검증 요약** (모두 실제 호출 없이 로컬에서 실행)
- 전체 테스트 1,001개가 통과한다(2차 리뷰 반영 전 834개). 개발자의 셸에 운영 DB URL·API 키·`AUTO_PUBLISH_ENABLED=true`가 내보내져 있어도 같은 결과다.
- 변이 테스트: 글 생성 파이프라인은 제가 고른 변이와 독립 리뷰어의 117개 하니스를 수정 후 코드에 다시 돌렸다. 리뷰어 하니스는 첫 실행에서 25개가 살아남았고, 테스트를 보강한 뒤 처음 살아남았던 11개가 모두 죽는 것까지 확인했다. 수정하며 바뀐 코드에 대해 별도로 만든 변이 52개도 모두 죽는다(처음 생존한 3개는 테스트를 고쳐 다시 확인). 발행기(63개)와 대시보드(103개)는 각 에이전트가 같은 방식으로 돌렸고 생존 0개로 보고했다. 그 뒤 2차 리뷰어가 발행기에 변이 66개를 돌려 8개가 살아남았고(그중 6개가 실제 공백), 리뷰어가 제안한 테스트로 모두 죽였다. 2차 리뷰 수정(최종 버튼 문구·재확인·가드·대화상자·대조군·글 주소·워커 중복 방지·재등록 이력·TTL 하한)에 대해 제가 따로 만든 변이 84개를 돌렸고, 처음 생존한 7개(후보 루프의 문구 검사, 대조군 호스트 검사, 메모리에 둔 글 주소 3곳, 글 주소 전달 2곳)에 테스트를 더해 모두 죽였다.
- 정제기 퍼징: 리뷰어의 입력 생성기로 약 44만 개를 넣어 허용 문법 위반 0건, 6,000개 출력은 실제 Chromium DOM으로 검사해 활성 요소·속성 0건.
- 실제 Chromium 재확인(로컬 가짜 사이트·대역 서버만 사용): 발행기 시나리오 7개와 `exp_verify_logic` 10개, 워커 강제 종료 후 복구, 대시보드 공격 4종(교차 출처 POST, 적대적 필드 XSS, 속성 주입, DNS 리바인딩). 2차 리뷰 뒤에는 리뷰어의 레이어 시나리오 12개(S1~S11), 경쟁·팝업·사전 열림·느린 리다이렉트·같은 제목 오래된 글, 워커 끝까지(S8, 검증 브라우저 실패, URL 소실·재큐·재시도), 강제 종료 6지점, 클레임 경쟁을 수정 후 코드로 다시 돌렸고, 제가 추가한 시나리오(사이트 전체 차단 5종·CDN 첫 요청 404·클라이언트 렌더링 등 익명 검증 11개, 문구가 거짓말하는 경쟁 10개, 레이어가 DOM을 계속 다시 그리는 3개)도 돌렸다. **어느 시나리오에서도 공개 글이 올라가지 않았다**(수정 전 S2b·S6·S8·S8b·S9·S11에서는 올라갔다).

**남은 위험과 사용자가 확인할 것**
1. **실제 Tistory UI는 한 번도 검증하지 못했다.** 발행기의 가정 A1~A12(비공개 라디오 값, 라벨 클릭, 최종 버튼 문구, 발행 후 주소 형태, 익명 접근 시 응답, '완료' 버튼 문구, 대조군 등)은 `app/publishing/tistory.py` 머리말에 있다. 가정이 틀리면 봇은 공개로 발행하지 않고 `UI_BROKEN`(최종 클릭 전) 또는 `PUBLISH_UNVERIFIED`(클릭 후)로 멈추도록 만들었다. 운영에 투입하기 전에 **비공개 글 1건으로 수동 드라이런**을 하고, 이미 공개된 글을 익명으로 열어 200과 제목이 보이는지도 확인할 것(봇 차단 화면의 403·리다이렉트를 비공개로 오인하지 않는지).
   - **2차 리뷰 수정으로 규칙이 더 엄격해졌다.** 실제 UI에서 ① 레이어를 여는 버튼 문구가 정확히 '완료'가 아니거나, ② 비공개를 고른 뒤 최종 버튼 문구에 '비공개'가 들어가지 않거나(`REQUIRED_FINAL_LABEL`), ③ 블로그 홈이 익명으로 `/`에서 HTTP 200으로 열리지 않으면, 발행은 매번 `UI_BROKEN`·`PUBLISH_UNVERIFIED`로 멈춘다(안전한 쪽의 실패). 드라이런에서 이 셋을 확인하고, 다르면 상수를 실제 값에 맞춘다.
   - 클릭 가드는 pointer·mouse·click 이벤트만 막는다(키보드로 발행하는 UI는 못 막는다). 글 주소만 골라 막는 익명 차단은 비공개와 구분하지 못한다. 새 탭에만 퍼머링크가 열리면 주소 없는 `PUBLISH_UNVERIFIED`로 멈춘다.
2. `PERPLEXITY_MODEL`/`ARTICLE_MODEL`의 `low` 이상 프리셋은 실호출에서 HTTP 400이었다. 제목 변경(`title_seed`, `title.flat`)과 `temperature` 우회도 실호출로 확인하지 못했다. 다음 실호출 1~2회로 확인하는 것이 좋다.
3. 대시보드는 이제 `127.0.0.1`·`localhost`·`::1` 외의 이름으로 접속하면 400이다. LAN·PC 이름·프록시로 접속하려면 `DASHBOARD_ALLOWED_HOSTS`에 넣고, 루프백이 아닌 `--host`로 열 때는 `DASHBOARD_PASSWORD`가 필수다.
4. `.env.example`은 여전히 `AUTO_PUBLISH_ENABLED=true`·`TISTORY_PRODUCTION_ENABLED=true`로 시작하고 작성자의 실제 블로그 이름·URL이 들어 있다(E2). 복사하면 발행이 켜지므로 `false`로 바꾸는 것을 권한다(사용자의 파일이라 바꾸지 않았다).
5. 본문 링크 신뢰 기준(검색 결과에 있었다)은 그대로다(§6 F3). 글은 비공개로 등록되므로 공개 전에 `warnings`의 외부 링크 알림을 확인할 것.
6. Python 3.10에서는 실행해 보지 못했다(문법은 3.10 기준으로 파싱 확인).

리뷰 도중 에이전트 한 곳이 옛 `tests/test_llm.py`(`requests.post` 패치)를 실행하다 외부 API로 401 요청 2건을 보낸 사고가 있었다(더미 키, 실제 자격 증명은 나가지 않음). 원인은 제가 생성기의 전송 계층을 바꾼 직후 테스트가 아직 그대로였던 짧은 시간 창이다. 재발 방지로 모든 테스트에서 외부 연결을 차단한다.
